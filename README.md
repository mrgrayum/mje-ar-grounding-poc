# MJE AR Grounding POC

Proof of concept: **temporary protective grounding in AR and 3D**, built on the MJE 3D and AR model library. A student views a utility structure, taps a conductor phase to place a ground clamp, taps a second point to place the other clamp, and a sagging ground cable is drawn between them. Every placement is recorded so the session can be exported as a JSON record.

Training visuals only. Nothing here is engineering data, and no structural or loading calculations are made.

- **Live site (GitHub Pages):** https://mrgrayum.github.io/mje-ar-grounding-poc/
- **Original library (untouched):** https://mrgrayum.github.io/mje-ar/
- **Demo content only.** This repository is public. Do not add real customer or equipment models.

## How the site is built

It is plain static files: no server, no database, no accounts.

| Path | What it is |
|---|---|
| `index.html`, `view.html`, `ar.html` | Library page, 3D model page (`view.html?m=<name>`), AR model page (`ar.html?m=<name>`) |
| `viewer.js`, `ar.js`, `library.js` | The three bundles. **Built from `src/`. Do not edit by hand.** |
| `library.json`, `models/<name>/` | Catalog, and per model: `model.glb`, `markers.json`, `preview.jpg` |
| `external/` | Niantic Spatial XR Engine and XRExtras, **copied unmodified** (license requirement). Never edit. |
| `src/` | Source of the web bundles (3D stage, markers, tour, AR page, library page) |
| `build-web.mjs` | Rebuilds the bundles. `npm run build` writes them; `node build-web.mjs --check` compares a fresh build with the files on disk |
| `serve.mjs` | Small local web server for desktop testing: `npm run serve`, then open http://localhost:8080/ |

To work on it: install Node 22 or newer, run `npm install`, edit `src/`, run `npm run build`, test, commit.

Rules for this project:

1. Grounding code lives in our own Three.js layer (`src/`), never inside engine files. If the engine license is ever withdrawn, 3D mode and grounding must still work.
2. The engine files in `external/` stay byte-for-byte as received.
3. No backend. Records are downloaded as a JSON file.
4. Page pinch-zoom stays blocked; pinch affects the 3D model only.

### Warning about the MJE AR Windows app

The Windows authoring app's **Publish to library** rewrites `viewer.js`, `ar.js`, `library.js` and the HTML pages with its own (older) copies. Once grounding code is added, publishing from the app into this folder would overwrite it. Until that is solved, publish models from the app only into a scratch folder and copy just `models/<name>/` and the `library.json` entry here.

## The test structure (Stage 1)

`tools/make-structure.mjs` generates a wood pole with a crossarm, three pin insulators, three conductors, a ground lead and a ground point. Re-run it (`node tools/make-structure.mjs`) after changing the numbers in `DESIGN` at the top of the file. Units are meters, Y is up, the power line runs along Z, the crossarm along X, the ground lead is on the +Z face of the pole. Phase B is carried on the pole top, A and C on the crossarm ends. Conductors (8 cm) and the ground lead (6 cm) are deliberately **exaggerated in thickness** so they can be tapped when the pole is shown about 2 m tall in AR. This is a training visual, not engineering data.

Required part (node) names, which the grounding code will rely on: `Pole`, `Crossarm1`, `InsulatorA`, `InsulatorB`, `InsulatorC`, `PhaseA_Conductor`, `PhaseB_Conductor`, `PhaseC_Conductor`, `GroundLead`, `GroundPoint`. Every part must have real geometry (see below). The three phases are the same color on purpose: students must identify them.

Tools: `node tools/check-nodes.mjs <file.glb>` lists the parts of any model; `node tools/optimize-check.mjs <file.glb>` runs the same steps as the app's "Optimize for phones" and compares every part before and after.

### Stage 1 findings: what the optimizer does to named parts

Tested on the generated structure, with optimization forced on (the app normally skips a file that would shrink by less than 3 percent; this one shrinks about 78 percent, so the real publish flow does optimize it).

1. **Names survive.** All 10 named parts are present, with the same hierarchy, after optimization. Identical shapes (for example the three insulators) are shared internally, but each keeps its own named part.
2. **Empty parts are deleted.** A part with no geometry (an empty marker node) is removed by the cleanup step. Every part that must survive needs real, visible geometry, which is why `GroundPoint` is a small copper block.
3. **Each part's own coordinate system is rewritten.** The compression stores every part's vertices in a small normalized range and moves the scale and offset into the part's own transform. Example: `Pole` goes from scale 1 to scale 6 and origin height 0 to 6, `PhaseB_Conductor` from scale 1 to 4.007. **Where the part sits in space does not change** (all parts match within 0.2 mm), but a point stored as `{node, local: [x, y, z]}` has different numbers before and after optimization.
4. **Consequence:** a record that stores `local` coordinates is only valid against the exact published `model.glb` it was made on. Re-publishing the model (re-optimizing) could shift stored positions. Options for the record format and the optimizer are written up with the Stage 2 plan.

## Ground mode (Stage 2, 3D viewer)

Available only on models whose `markers.json` has `"grounding": true` (add `?ground=1` to a model address to try it on any model), and not in embedded frames. The **Ground mode** button sits under the 3D / AR switch. While it is on, marker badges and tour arrows are hidden and a panel shows what to do next, the list of grounds, **Undo last** and **Clear all**; each row has a ✕ to delete just that pair.

- **Tap = place.** A tap must move less than 6 px and last under 0.5 s; anything else is a drag (rotate/zoom) and places nothing. Tapping empty space does nothing.
- **First tap** places a pulsing clamp on the part under the finger. **Second tap** places the other clamp and draws a green cable between them. The next tap starts the next pair (G1, G2, G3...).
- **A clamp on a wire always hangs down.** Whichever side of a conductor is tapped (top, side or underneath), the clamp body goes on the underside of the wire right below the tapped spot and its cable eye points straight down, so the cable hangs from it. Tapping the underside gives the same clamp, so the rule is repeatable (checked: above, side and underneath give the same position within about 1 cm). On other parts (pole ground, blocks) the clamp keeps the direction of the surface but never points upward. The recorded `normal` of a clamp on a wire is therefore straight down; older records whose clamps pointed up are redrawn hanging down when loaded (`clampPose` in `src/grounding.js`).
- **Clamps belong to the part.** Each clamp is a child of the tapped part's node, at the tapped point on its surface, so it moves with that part. Its size is corrected for the part's own scale (see Stage 1 findings).
- **Cable sag (hangs under gravity).** The cable is longer than the distance between its ends (`CABLE_SLACK`, 12 percent by default) and its shape is found by letting a chain of points settle under gravity (`hangingCable` in `src/grounding.js`): it keeps its length, hangs in a U with its lowest point below both ends, resists sharp bends a little (`CABLE_STIFFNESS`), stays above the floor and is kept out of tall, thick parts such as the pole. A near-vertical run (phase to pole ground) can only use its slack by bowing out, so it swings away from the surfaces it is clamped to and hooks into its clamp. Measured on the test pole: lowest point below both ends in every case, 4 to 11 ms to settle per cable, same shape in 3D and AR. To make cables hang looser or tighter, change `CABLE_SLACK` (for example 0.2 or 0.08).
- **Settings** (cable slack and stiffness, sizes, colors, tap limits) are in `GROUND_CONFIG` at the top of `src/grounding.js`. Sizes are fractions of the model's radius, so they scale with any model.
## Session record (Stage 3): export, load, refresh protection

Format and code: `src/grounding-record.js`. Session panel fields: **Student name** (required to export) and **Class** (optional).

```json
{ "format": "mje-grounding-record", "version": 1,
  "model": { "slug": "test-pole-structure", "title": "Test Pole Structure", "bytes": 19628, "fingerprint": "c3dc2e6173879dbe" },
  "student": "...", "scenario": "...",
  "sessionStart": "time of the first clamp", "sessionEnd": "time of the export",
  "grounds": [ { "id": "G1",
                 "a": { "node": "PhaseB_Conductor", "local": [x,y,z], "model": [x,y,z], "normal": [x,y,z] },
                 "b": { "node": "GroundLead",       "local": [x,y,z], "model": [x,y,z], "normal": [x,y,z] },
                 "placedAt": "time" } ] }
```

- `node` is the name of the part tapped; `local` is the point in that part's own coordinates; `model` is the same point in the model's overall coordinates; `normal` is which way the surface faced (model coordinates).
- **Why `model` and `normal` are in the file.** Stage 1 showed `local` changes whenever a model is re-optimized. Reloading therefore draws from `model` (stable), attached to the part of that name, and uses `normal` to turn the clamp the right way. `local` stays in the file for the record and for auditing.
- `model.bytes` and `model.fingerprint` (first 16 characters of the model file's SHA-256) identify the exact file. If they differ on loading, the record still loads, with a note that the model was updated. A record for a different model (`slug`) is refused. A record that names a part missing from the model draws the other grounds and says how many it skipped.
- **Export record** downloads `grounding-record_<student>_<yyyymmdd-hhmm>.json`. **Load record** shows a saved file on the model read-only (add, undo, clear, delete and export are off); **Close record** returns to the live session, which is set aside untouched.
- **Refresh protection.** After every change the placed grounds, student name and class are saved in the browser's local storage, one slot per model (`mje-grounding:<slug>`). On page load a saved session is redrawn with a note and **Start fresh** clears everything, including the saved copy. It never clears by itself. It lives only in that browser on that device (not shared, not backed up; lost by private windows or clearing site data). A first clamp that is still waiting for its partner is not saved. While a record is being viewed, nothing is saved.

## Ground mode in AR (Stage 4)

The AR page (`ar.html`) uses the same grounding code as the 3D page (`src/grounding.js`), wired in by `src/ar-main.js` for models with `"grounding": true`. The grounding code only needs a camera, the model and a per-frame tick, so it works without the AR engine as well.

- **Lock & Ground** appears once the model is placed. Pressing it locks the model (one finger no longer turns it, two fingers no longer resize it, Move model and the marker controls hide) and turns Ground mode on; the same button then reads **Unlock**. Unlock turns Ground mode off so the model can be moved or resized; grounds already placed stay on their parts and move with the model. Tip: pinch the model larger *before* locking, because at AR size the wires are only a few pixels wide.
- **Fingertip snapping.** A mouse must hit a part exactly. A finger also looks for thin, wire-like parts (under 14 px thick on screen) within 24 px of the touch, using the real shape of every part, and takes the thinner one when it is close; a thin part right under the finger beats a thinner one 20 px away. Parts hidden behind other parts are skipped. Measured on the stand-in test below (phone-sized screen, model about 2 m tall): visible conductors picked correctly 83 to 100 percent of the time at a 6 px miss, 78 to 94 percent at 10 px, 72 to 86 percent at 14 px (most wrong picks were the neighbouring conductor), better when the model is enlarged.
- **Phone panel.** On narrow screens (and always in AR) the panel is a slim bar: instruction line, **Undo last**, **Clear all**, **More**. More opens the student name and class boxes, the list with a delete button per ground, **Export record**, **Load record** and **Start fresh**. Wide screens keep the full side panel.
- **Export from a phone** hands the record file to the system share sheet (Files, Mail, AirDrop) when the browser supports sharing files; otherwise it downloads the file. The share sheet being closed without choosing anything saves nothing and says so.
- Same record file, refresh protection and read-only loading as on the 3D page.

How the AR page was tested on a PC: `ar.html?m=...&force=1` with a stand-in for the AR engine (a camera, a renderer and the pipeline calls, nothing else) driven frame by frame; the page's own code for placement, gestures, locking and grounding ran unchanged. This does not test real camera tracking, real touch screens or the share sheet on a phone.

## Names and structure details (Step B, record version 2)

- **Naming a conductor.** The first time a conductor is tapped, a small box appears at the top of the panel: quick buttons (A Phase, B Phase, C Phase, Neutral, Static, plus the name suggested from the part), a text box for the term your line uses, **OK** and **Skip** (Skip keeps the suggested name). Taps on the model are ignored until it is named, and **Undo last** cancels both the clamp and the question. After that, the same conductor is never asked about again. A conductor is any part whose name contains "conductor" (the `isConductor` rule in `src/grounding.js`); other parts get plain default names (`PART_LABELS`: Pole ground, Ground point...).
- **Structure setup** (a folded section in the panel; on a phone it is inside **More**). Structure / pole number, line or circuit name, job / work order number, and **Name conductors by tapping**: press the button, then tap any wire on the model. The wire lights up yellow, the name box opens (prefilled if it already has a name, with **Cancel** instead of **Skip**), and when it is named a small yellow **name tag** appears on the wire where it was tapped. Taps on anything that is not a conductor say so and do nothing. Press **Done** (a yellow bar at the top of the panel) when finished. Named conductors are listed by their given names ("B Phase ✎", tap to rename) with a count ("2 of 3 conductors named"); the model's internal part names are never shown. Naming while adding grounds works the same way (the wire lights up and the tag appears). Tags are **off by default**: a switch in Structure setup, **Show conductor name tags on the model**, turns them on (saved with the session; Start fresh puts it back to off). When on they appear only in Ground mode (not on a saved record that is being viewed) and keep a constant size on screen (`TAG_HEIGHT` in `src/grounding.js` sets their size). After naming in name mode, the instruction line confirms the name ("Named \"B Phase\". Tap another wire, or press Done."), since no tag appears. Renaming a conductor updates every ground that uses it.
- **Where the names show up:** the ground list (`G1: B Phase → Pole ground`), the instruction line, the viewed-record banner (with the structure number and line), and the exported record. **Clear all** keeps the names and structure details; **Start fresh** clears them too.
- **Record version 2** (`src/grounding-record.js`): adds `structure {number, line, job, conductors {PartName: "Name"}}`, a `label` and `kind: "clamp"` on every end, and an empty `fittings` list reserved for the cluster bracket and ground rod (next step). The file name now includes the structure number (`grounding-record_p-123_alex-rivera_20261123-1332.json`). **Version 1 records still load**: they are filled in with empty structure details and suggested names, and say so. Everything is saved on the device with the session, so a refresh keeps the names and structure details.

## Cluster bracket, ground rod and smart taps (Step C)

- **What a tap does** (decided by the part's name in `src/grounding.js`, `tapKind` and the `*_PART` settings): a **wire** (any part with "conductor" in its name) or the **pole ground** (name contains "ground" or "lead") gets a clamp, as before; the **pole** gets a **cluster bracket** at the tapped spot; the **square U of a bracket** gets a ground clamp exactly like a wire does; the **ground beside the pole** (within `ROD_REACH` of the pole, about 2 m on the test pole) gets a **ground rod**; a rod that is already there takes a cable. The crossarm and insulators are not used: the panel says so. Taps further away from the pole on the ground say what can be tapped.
- **Joining.** The first tap starts a ground, the second one finishes it, whatever the two things are: wire to U clamp, U clamp to pole ground, U clamp to rod, rod to pole ground, wire to wire. Tapping the pole only places the bracket (nothing is connected yet): tap its U, then the other end. A clamp on the U hangs down from the underside, with the cable eye pointing down, just like a clamp on a wire; there are no studs or terminals, and a U takes as many clamps as fit on it.
- **Several clamps on a bracket.** Any number of clamps can go on the U (all the phases, a jumper to the pole ground, and so on). The rod takes any number of cables on its eye.
- **Looks.** The bracket is drawn after the chain-type pole clamp in the project owner's photo, reduced to its two main parts: a zinc **chain** that wraps round the pole (sized to the pole at the tapped spot) and a square gray **U that lies level and sticks straight out from the pole** (about 0.2 m long and 7 cm thick on the test pole; `zf` and the bar sizes in `makeFittingBuilder` set it). The arms start where the chain ends are. It faces the side of the pole that was tapped. There is no jaw, handle or tensioner. The rod is copper with a dark cap and eye on a small ground pad. Both are drawn at about the same exaggerated scale as the clamps (`FITTING_SIZE`). The cables use the same hanging-cable physics.
- **Undo, delete, Clear all.** Undo removes the waiting item, otherwise the last thing made (a ground, a bracket or a rod, in the order they were made; a rod goes with its last cable). The list has a **Hardware** section (bracket and rod with their cable counts); its ✕ removes the piece and every cable on it (asks first when it has cables). Clear all removes everything.
- **Fingers.** On a phone a finger that is on the pole means the pole (so a bracket can be added), even with the thin pole ground right beside it; wires still snap from a distance; a finger that lands on or beside a bracket picks the nearest place on its U and a finger on a rod picks the rod.
- **Record.** The `fittings` list is now used: `{id: "B1", type: "cluster_bracket" | "ground_rod", label, node, local, model, normal, placedAt}`. A clamp on a bracket's U is an ordinary clamp end whose `node` is the bracket's id (`{kind: "clamp", node: "B1", ...}`); a rod is a `{kind: "fitting", fitting: "R1", label, slot}` end. (Records made on 2026-11-23 before this change, with cables fastened to bracket studs, still load but those cables are skipped.) The version stays 2. Older version 2 records (no hardware) and version 1 records still load. Hardware is saved with the session, restored after a refresh and drawn on a viewed record.

## AR smoothing: calming the shake when the phone is held still

- **The cause.** The phone's tracking reports the camera's position and direction with tiny errors (a millimetre or two, a fraction of a degree) that change every frame. The model is fixed in the room, so the errors show up as the model trembling when you hold still. Walking or turning hides it, because the real movement is much bigger.
- **The fix** (`src/smooth.js`, used by `src/ar-main.js`). A "One Euro" filter averages those errors out of the camera pose that our own code uses for drawing, card positions and taps: the slower the phone moves, the more it smooths, and when the phone really moves or turns it lets that through with almost no delay. A jump in the tracking (it found its position again, or **Move model** recentred the world) restarts the filter instead of being smoothed. The AR engine files are not touched.
- **Settings, in the address of the AR page:** `&smooth=off`, `light`, `normal`, `strong` or `max` (the default, since the owner's phone test found it the best of the settings tried). `strong` and `max` also have a **hold-still zone**: the drawn view stays exactly where it is until the smoothed pose has moved a little further away than the zone (2 mm and 0.08 degrees on `strong`, 4 mm and 0.15 degrees on `max`), so tiny wobble never reaches the screen but real movement and slow drift do. Add `&meter=1` for a small box at the bottom left with frames per second and two wobble figures (position in mm and turn in degrees over the last second, as reported by the phone ("raw") and as used for drawing ("shown")); hold the phone still to compare settings. Example: `ar.html?m=test-pole-structure&smooth=max&meter=1`.
- **What was measured (simulated tracking noise on a PC, not a real phone).** Still: frame-to-frame jitter drops by roughly 60% on `normal`, and on `strong` and `max` the turn jitter falls to almost nothing (the zone holds the view). Walking at 0.4 m/s the drawn view trails the real position by about 4 mm on `normal`, 6 mm on `strong` and 8 mm on `max`; turning at 60 degrees per second it trails by about 0.17, 0.25 and 0.3 degrees (raw tracking is about 0.13). Real tracking noise differs, so the settings may need adjusting after tests on a phone. If a strong setting still shows shake, the phone's tracking itself is losing its hold on the room (a plain floor, dim light or fast movement), which smoothing can only hide, not fix.

## Models without markers, and the motion-permission popup

- **No markers, no marker controls.** A library model whose `markers.json` has no markers no longer shows the marker menu, the arrows or the "No markers" text, in 3D or in AR (`src/viewer-main.js`, `src/ar-main.js`). Models with markers are unchanged. The grounding test pole has had its two sample markers removed (they were only samples; the library entry now says 0 markers).
- **The motion-permission popup** ("AR requires access to device motion sensors", Cancel / Continue) comes from the AR engine, which we may not edit. Its wording is the engine's own, but it is drawn with ordinary page elements, so `src/ar-main.js` restyles them to our theme: a black panel with a yellow top edge, white text, a grey Cancel button and a yellow Continue button. Checked on a PC against a copy of the popup's markup, not on a phone.

## How the model appears in AR (placement animation)

Each model has its own setting, `"intro"` in its `markers.json` (`grow`, `drop`, `scan`, `assemble` or `off`; a model with no setting appears without animation, as before). The owner chose **scan** for the test pole, so it is set there; the authoring app gets a menu for it. The address of the AR page can override the setting for testing with `&intro=`. The four styles: **`grow`** (the model grows out of the spot you tapped, with a small overshoot and settle), **`drop`** (it falls from above, lands with a bounce and squash, and a ring of dust spreads over the floor), **`scan`** (a glowing MJE-yellow ring sweeps up the model from the floor and the model only exists below it), **`assemble`** (the parts fly in one after another, lowest first, popping into place; tall parts such as the pole grow up out of the floor) and **`off`**. Every style also sends a yellow ripple across the floor from the tapped spot. It plays each time the model is placed, including after **Move model**, takes about 1 to 1.7 seconds, and leaves every position, size and material exactly as it was. A phone set to "reduce motion" gets no animation unless `&intro=` is given. Example: `ar.html?m=test-pole-structure&intro=scan`. The code is in `src/intro.js`; the animation moves a group between the user's anchor and the model, so turning and resizing are not affected. While `assemble` plays, grounding clamps and cables are hidden and shown again at the end. Tested on a PC stand-in only; the feel has to be judged on a phone.

## Structure builder

Open `build.html` (https://mrgrayum.github.io/mje-ar-grounding-poc/build.html). A toolbox on the left builds a structure from parts; **Ground this structure** opens it in the same grounding tool as any library model.

- **Recipe**: a structure is a small piece of data (`src/structure/recipe.js`, format described at the top of the file): structure type, height, arm spacing, one length for every arm on the right and on the left (0 to 6 arms per side), an optional phase on top of a pole, insulator, details, guy wires. **All sizes are in feet** (height 20 to 110 ft, arm length 0 to 15 ft). The same recipe always builds the same structure. **Save recipe** downloads it, **Download .glb** downloads the model.
- **Parts** (`src/structure/parts.js`): wood pole, **lattice tower** (four leaning legs, belts and X bracing), wood arm, **steel truss arm**, standoff bracket, suspension insulator string (glass or polymer, 1 to 24 bells), pin insulator (porcelain or polymer, upright or lying on its side as a standoff), phase conductor, down ground, static wire, guy wire and anchor. Part names follow the grounding tool's rules (`Pole`, `Crossarm_C`, `InsulatorC`, `PhaseC_Conductor`, `GroundLead`, `TowerLeg_1`), so every wire can be clamped, a wood pole takes a bracket, tower legs and braces take a clamp, and arms and insulators are not clamp targets.
- **Arms and names**: each arm carries one wire and its letter names them together: arm C holds `PhaseC_Conductor` and `InsulatorC`. Letters run top phase first (if any), then the right arms top to bottom, then the left arms. **Up / down**: every arm can be moved up or down (in feet) from its default place, or put at level 1, 2, 3 and so on with one tap, so a lone arm on the other side can sit at the top, middle or lower level; the panel shows the arm's height above ground, and notes warn when two arms on a side are too close for the insulator. An arm shorter than 6 in becomes a **standoff** (a pin insulator lying on the side of the pole or tower, or a short steel bracket under a hanging string). If an insulator is too long for the arm spacing, the spacing grows and a note says so. Quick layouts set common arm counts in one tap.
- **Dead end**: each arm has a Dead end option (and one switch for every arm). The wire stops at the arm: a strain string lies along the line on each side of the arm tip (`InsulatorC_Front`, `InsulatorC_Back`, bells and glass or polymer from the Insulators section), each holds one end of the wire, and a jumper hangs down between the two string ends. The two spans and the jumper are one mesh named `PhaseC_Conductor`, so the grounding tool sees one wire, one phase, and a clamp anywhere on it is on that phase. **Terminal dead end**: the same, with the line on one side only (front is the +Z side, the side of the down ground; or back): one strain string, and the wire is left as a free tail hanging down on the structure side, still one mesh and one phase. Each arm has a Line end choice (through, dead end, terminal front, terminal back) and there is one choice for every arm. A dead-end arm is drawn at least 1.5 ft long, and the arm spacing grows to leave room for the jumper. Wood pole and lattice tower.
- **Pole-top phase** (wood pole): a real phase on top of the pole, on its own **pole-top pin insulator** (porcelain or polymer) or a suspension string on a short bracket, chosen separately from the arm insulators. It is wire A, apart from the static (shield) wire, and the two can be used together.
- **Guy wires**: up to four, each with a direction around the pole (0 to 355 degrees, 0 = along the line on the side of the down ground, 90 = toward the right arms), a distance out to the anchor and a height up the pole. Wood pole only.
- **Adding to the toolbox**: structure types, arm types and insulator types are lists in `recipe.js` (`STRUCTURES`, `ARM_TYPES`, `INSULATORS`); items marked `ready: false` show as "coming soon". A new part is one function in `parts.js` and one place in `buildStructure`.
- Sizes are nominal and wires are deliberately thick. Training visual, not an engineering drawing.
